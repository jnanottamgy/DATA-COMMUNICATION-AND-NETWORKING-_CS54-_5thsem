Recursive and iterative DNS resolution
CO1in BOTH of the last two CIE-1s5 marksdraw it

Setup: host cse.nyu.edu wants the IP of gaia.cs.umass.edu; its local server is dns.nyu.edu.

Iterative — the real case. 5 steps, 8 messages

  1. Host → local DNS server (this first hop is always recursive)
  2. Local → root; root returns the IP of the .edu TLD server
  3. Local → TLD; returns the IP of the authoritative server dns.umass.edu
  4. Local → authoritative; returns the IP of the host
  5. Local DNS server → host

Each server says "I don't know, but ask this one" — so the local server does all the work. 8 messages = 4 queries + 4 replies.

Recursive

host → local → root → TLD → authoritative, each server querying the next on behalf of the previous; the answer travels back down the same chain. Load shifts upward onto the higher-level servers.

RecursiveIterative
"Find me the complete answer" — the receiving server is responsible for getting it"If you don't know, tell me whom to ask next" — returns the best info it has
More load on root / TLD serversWork done by the local DNS server
Last markAdd: "DNS caching at the local server lets steps 2–4 be skipped next time, until the TTL expires." In the real Internet it is hybrid: host→local recursive, everything after that iterative.

Cookies — keeping user state over stateless HTTP
CO1came in CIE-1 Apr 20255 marksdraw it

Why: HTTP is stateless — the server forgets the client the moment it replies. Cookies let a site identify a user across requests and across visits.

The 4 components — write all four

  1. A Set-cookie: header line in the HTTP response
  2. A Cookie: header line in subsequent requests
  3. A cookie file on the user's machine, managed by the browser
  4. A back-end database at the website

Amazon login — 6 steps

  1. User logs in: browser sends POST /ap/signin with username and password.
  2. Server creates a unique ID (session-id = ABC123), stores it in its database against this user, replies Set-cookie: session-id=ABC123.
  3. Browser saves it in its cookie file (amazon → ABC123).
  4. On every later request the browser automatically adds Cookie: session-id=ABC123.
  5. Server looks the ID up, recognises the user, returns personalised content — no password again.
  6. A week later the cookie is still sent (until it expires), so the user is still recognised.

Go-Back-N with a lost frame (+ the Selective Repeat window)
CO23 CIE-1s: 2025, 2024, 20215 marksdraw it

1. Idea

GBN is a reliable-data-transfer (ARQ) protocol. The sender may send up to N packets without waiting for ACKs. If a packet is lost, the sender goes back and retransmits that packet and every packet after it.

2. Sender

Window of size N with base (oldest unACKed) and nextseqnum. ONE timer, for the oldest unACKed packet. Cumulative ACKs — "ACK n" means all packets up to n arrived. On timeout it resends base … nextseqnum−1.

3. Receiver

Accepts only the expected in-order packet (delivers + ACKs it). Any out-of-order or corrupted packet is DISCARDED and the ACK of the last in-order packet is re-sent. The receiver has no buffer.

5. Drawbacks

  • Correctly received packets after the loss are thrown away and resent → wasted bandwidth.
  • Poor on noisy networks — one loss costs a whole window.

4. Sequence diagram, N = 4, packet 2 lost

If it asks SR window = 2m−1The receiver buffers out-of-order packets, so sender and receiver windows must never overlap: Ws + Wr ≤ 2m → W ≤ 2m−1. With m = 2: W = 3 fails (all ACKs lost, resent pkt 0 is accepted as new data — an error); W = 2 works (the resent 0 is outside the receiver's window 2,3, so it is recognised as a duplicate and re-ACKed).
HookGBN = one timer, no buffer, cumulative ACK, resend everything. SR = many timers, buffer, individual ACK, resend one.

Three-way handshake and connection termination — significance of each step
CO2CIE-1 Apr 2025 & Jun 20235 marksdraw it

A. Establishment — 3 segments

  1. SYN. Client sends SYN = 1 with a randomly chosen client_isn. No data.
    Significance: asks to open the connection and tells the server where the client's byte numbering starts.
  2. SYN + ACK. Server replies SYN = 1, its own server_isn, ack = client_isn + 1, and allocates buffers.
    Significance: agrees to connect, confirms the client's number and announces its own.
  3. ACK. Client sends SYN = 0, seq = client_isn + 1, ack = server_isn + 1, allocates buffers; may already carry data.
    Significance: confirms the server's number — connection is ESTABLISHED.

Why three: each side must announce its own initial sequence number and have it acknowledged by the other. Two steps cannot do both.

B. Termination — 4 segments

  1. FIN from the client (no more data to send)
  2. ACK from the server — the client→server direction is now closed
  3. FIN from the server (it has finished too)
  4. ACK from the client — resources deallocated at both ends

Why four: TCP is full-duplex, so each direction is shut down separately. The client first waits in TIME_WAIT (~30 s) so a lost final ACK can be re-sent and old segments can die out.

If it says "states" insteadDraw the ring of 6 client states and label every arrow event / action: CLOSED →(connect, send SYN)→ SYN_SENT →(rcv SYN+ACK, send ACK)→ ESTABLISHED →(app closes, send FIN)→ FIN_WAIT_1 →(rcv ACK)→ FIN_WAIT_2 →(rcv FIN, send ACK)→ TIME_WAIT →(30 s)→ CLOSED. First three = setup, last four = termination.

Flow control and the receive window (rwnd)
CO2CIE-1 May 2024 & Jun 20235 marks

Problem: if the network layer delivers data faster than the application reads it, the receive buffer fills and overflows — data is lost.

Solution: TCP flow control — a speed-matching service that matches the sender's rate to the receiving application's reading rate.

The receiver keeps RcvBuffer plus LastByteRead and LastByteRcvd. To avoid overflow:

LastByteRcvd − LastByteRead ≤ RcvBuffer
rwnd = RcvBuffer − [LastByteRcvd − LastByteRead]
LastByteSent − LastByteAcked ≤ rwnd

The receiver advertises rwnd in the receive-window field of every ACK. When rwnd = 0 the sender stops but keeps sending small probe segments so it learns when space frees up.

Worked exampleRcvBuffer = 4096 B, LastByteRcvd = 3000, LastByteRead = 1000.
rwnd = 4096 − (3000 − 1000) = 2096 B — the sender may have at most 2096 bytes unACKed. If the application then reads up to byte 3000, rwnd rises back to 4096 B.
Hookrwnd protects the receiver, cwnd protects the network. Data actually in flight = min(cwnd, rwnd).

Subnetting design — unequal sub-blocks from one granted block
CO3most-asked Unit 3 topic — 5 past questions6–9 marks
"An organization is granted a block with the beginning address 14.24.74.0/24. It needs three subblocks: one of 10 addresses, one of 60 and one of 120. Design the sub-blocks."

Step 1 — the given block

n = 24 → N = 232−24 = 28 = 256 addresses: 14.24.74.0 to 14.24.74.255.

Step 2 — the 3 rules (write them, they carry marks)

  1. Each subnet size must be a power of 2 — round every requirement up.
  2. nsub = 32 − log2 Nsub
  3. Each start address must be divisible by its own size — which happens automatically if you allocate the largest first.

Step 4 — leftover

Used = 128 + 64 + 16 = 208. Unused = 256 − 208 = 48 addresses: 14.24.74.208 – 14.24.74.255.
