Recursive and iterative DNS resolution
asked in BOTH last two CIE-1s5 marksCO1draw it
"Illustrate how recursive and iterative DNS resolution processes work." CIE-1 Apr 2025 Q1a · CIE-1 May 2024 Q1b

Setup for both: host cse.nyu.edu wants the IP of gaia.cs.umass.edu. Its local DNS server is dns.nyu.edu.

A. Iterative resolution — the usual case (Fig. 2.19)

  1. Host → local DNS server: query. (This first hop is always recursive.)
  2. Local → root server; root replies with the IP of the .edu TLD server.
  3. Local → TLD server; it replies with the IP of the authoritative server dns.umass.edu.
  4. Local → authoritative server; it replies with the IP of gaia.cs.umass.edu.
  5. Local DNS server → host: the final answer.

Each contacted server says "I don't know, but ask this server", so the local server does all the work. Total = 8 messages (4 queries + 4 replies).

B. Recursive resolution (Fig. 2.20)

host → local → root → TLD → authoritative, each server querying the next on behalf of the previous one. The answer travels back down the same chain: authoritative → TLD → root → local → host. The burden shifts upward onto the higher-level servers.

RecursiveIterative
"Find me the complete answer." The server that receives the query is responsible for getting the final answer."If you don't know, tell me whom to ask next." The server returns the best info it has — usually another server's address.
Puts more load on higher-level (root/TLD) servers.Work is done by the local DNS server; this is the usual mode for queries leaving the local server.
HookRecursive = Responsibility passed upward (one chain up, one chain down). Iterative = I'll do it myself (local server bounces off each server in turn). In the real Internet it is hybrid: host→local is recursive, everything after that is iterative.

Cookies — keeping user state over stateless HTTP
came in CIE-1 Apr 20255 marksCO1draw it
"How would a web server use cookies to remember a user's login session across multiple visits? Illustrate with an example." / "Describe user-server interaction using cookie technology." CIE-1 Apr 2025 Q2a · SEE Feb 2024 Q2b

Why cookies exist: HTTP is a stateless protocol — the server forgets a client the moment it replies. Cookies let a site identify a user across requests and across visits (login sessions, shopping carts, recommendations).

The 4 components (always write all four)

  1. A Set-cookie: header line in the HTTP response.
  2. A Cookie: header line in subsequent HTTP requests.
  3. A cookie file on the user's machine, managed by the browser.
  4. A back-end database at the website.

Example — Amazon login session

  1. User logs in: browser sends POST /ap/signin with username and password.
  2. Server creates a unique ID (e.g. session-id = ABC123), stores it in its database against this user, and replies with Set-cookie: session-id=ABC123.
  3. The browser saves it in its cookie file (amazon → ABC123).
  4. On every later request ("My Orders") the browser automatically adds Cookie: session-id=ABC123.
  5. The server looks the ID up in its database, recognises the logged-in user, and returns personalised content — no password asked again.
  6. A week later the browser still sends the cookie (until it expires), so the user is still recognised.
HookFour components = "Set it, Send it, Store it, Search it" → Set-cookie header · Cookie header · cookie file in the browser · back-end database. Cookies make a stateless protocol behave statefully.
Scoring key"HTTP is stateless" opening line (1) · the 4 components (1.5) · the timeline diagram (1.5) · the numbered Amazon example (1).

Electronic mail — SMTP sequence, SMTP vs HTTP, POP3 vs IMAP
email = 5 questions · came in CIE-1 Apr 20255–8 marksCO1draw it
"Illustrate the sequence of events when SMTP is used to send an email from User A to User B, where the servers are different." CIE-1 Apr 2025 Q3b · SEE Feb 2024 Q1a (compare SMTP/FTP/HTTP) · SEE Jan 2020 Q1c (POP3 vs IMAP)

3 major components of email: user agents (Outlook, Gmail app — compose/read/reply/forward), mail servers (hold each user's mailbox + an outgoing message queue), and SMTP (the protocol that pushes the mail).

The 6 steps to write

  1. User A writes a message to B's address in A's user agent.
  2. The user agent sends it to A's mail server, where it is placed in the outgoing message queue.
  3. The SMTP client side on A's server opens a TCP connection to port 25 on B's mail server.
  4. After SMTP handshaking (sender and recipient addresses are agreed), the client sends A's message over that TCP connection.
  5. B's mail server (SMTP server side) places the message in B's mailbox.
  6. User B runs their user agent and reads it — fetched with POP3, IMAP or HTTP.

S: 220 hamburger.edu C: HELO crepes.fr S: 250 Hello crepes.fr, pleased to meet you C: MAIL FROM: <alice@crepes.fr> S: 250 Sender ok C: RCPT TO: <bob@hamburger.edu> S: 250 Recipient ok C: DATA S: 354 Enter mail, end with "." on a line by itself C: Do you like ketchup? C: . S: 250 Message accepted for delivery C: QUIT S: 221 closing connection

Persistent vs non-persistent HTTP (with the RTT count)
asked 2×5–6 marksCO1numerical inside
"Explain HTTP with non-persistent connections with an example." / "Differentiate between persistent and non-persistent TCP connections used in HTTP." SEE Jan 2020 Q1a · Makeup Feb 2020 Q1a

Non-persistent: each request/response pair uses a separate TCP connection, which the server closes after sending the object. Default in HTTP/1.0.
Persistent: one TCP connection is reused for many requests; the server keeps it open for a while. Default in HTTP/1.1.

Standard example — 1 HTML page + 10 JPEGs = 11 objects

  1. 1a. Client opens a TCP connection to www.someSchool.edu on port 80. 1b. The server, waiting on port 80, accepts it.
  2. Client sends an HTTP request with the path /someDepartment/home.index into its socket.
  3. Server reads it, puts the object in an HTTP response and sends it.
  4. Server closes the TCP connection.
  5. Client receives the HTML, displays it, parses it and finds the 10 JPEG references.
  6. Steps 1–5 repeat for each JPEG → 11 TCP connections in total.
Response time per object = 2 RTT + transmit time   (1 RTT to set up TCP, 1 RTT to request & start receiving)

HTTP message format + conditional GET
asked 2×, both in CIE-1s5–6 marksCO1
"Draw the general format of an HTTP request message and give an example of request and response messages using conditional GET." / "Interpret the meaning of each line of the HTTP message below." CIE-1 Jun 2023 Q1a · CIE-1 May 2024 Q3a

1. General format of a request message

method sp URL sp version cr lf ← request line header field name: sp value cr lf ← header lines ... (one or more) header field name: sp value cr lf cr lf ← blank line entity body ← empty for GET

Reading a real request, line by line

GET /somedir/page.html HTTP/1.1 Host: www.someschool.edu Connection: close User-agent: Mozilla/5.0 Accept-language: fr
  • Request line — 3 fields: method GET (browser is asking for an object), URL (path of the object), version.
  • Host: names the host the object resides on. Needed because one server can host many sites; used by web proxy caches.
  • Connection: close — the browser asks the server to close the TCP connection after this object (it does not want persistence).
  • User-agent: the browser type. The server can send different versions of an object to different browsers.
  • Accept-language: fr — the user prefers the French version; if none exists the server sends its default.

Always add: a blank line (extra CRLF) ends the headers, and the entity body is empty for GET (used for POST).

2. Conditional GET

A conditional GET = a GET carrying an If-Modified-Since: header. It asks the server to send the object only if it has changed since that date. Used by web caches to make sure a stored copy is not stale.

First request & response — the cache stores the object and its Last-Modified date:

GET /fruit/kiwi.gif HTTP/1.1 Host: www.exotiquecuisine.com HTTP/1.1 200 OK Date: Sat, 3 Oct 2015 15:39:29 Server: Apache/1.3.0 (Unix) Last-Modified: Wed, 9 Sep 2015 09:23:24 Content-Type: image/gif (data data data ...)

A week later the cache re-checks:

GET /fruit/kiwi.gif HTTP/1.1 Host: www.exotiquecuisine.com If-modified-since: Wed, 9 Sep 2015 09:23:24 HTTP/1.1 304 Not Modified Date: Sat, 10 Oct 2015 15:39:29 Server: Apache/1.3.0 (Unix) (empty entity body)

304 Not Modified tells the cache its copy is still valid — the object is not re-sent, saving bandwidth.

Definition: OSI (Open Systems Interconnection) is a reference model published by ISO (the organisation, founded 1947) in the late 1970s. It is a model, not a protocol — a 7-layer framework for designing flexible, robust and interoperable architecture. An open system is a set of protocols that lets any two different systems communicate regardless of their underlying architecture.

Web caching / proxy server

A web cache (proxy server) sits between clients and origin servers and keeps copies of recently requested objects. The browser is configured so all requests go to the cache first. The cache is both a server (to the browser) and a client (to the origin server).

4 steps: (1) browser opens a TCP connection to the cache and sends the request; (2) hit → cache returns the object; (3) miss → cache opens a TCP connection to the origin server and fetches it; (4) cache stores a copy and forwards one to the browser.

3 benefits: lower response time (cache is near the client) · less traffic on the institution's access link (no costly upgrade) · less web traffic on the Internet overall.

The numerical: LAN 100 Mbps, access link 15 Mbps, objects 1 Mbit, 15 req/s, Internet delay 2 s.
Access-link traffic intensity = (15 × 1)/15 = 1 → delay grows without bound. LAN intensity = 15/100 = 0.15, negligible.
Option 1 upgrade link to 100 Mbps → intensity 0.15, response ≈ 2 s, but costly.
Option 2 install a cache, hit rate 0.4 → 40% served from the LAN in ~10 ms, only 60% use the access link (intensity 0.6).
Average delay = 0.4 × 0.01 + 0.6 × 2.01 ≈ 1.2 s — faster than the upgrade and much cheaper.

P2P vs client-server file distribution

Notation: file size F, N peers, server upload us, peer i upload ui, slowest download dmin.

Dcs = max { NF/us , F/dmin }

Framework — the 3 questions classic TCP answers

  1. How does the sender limit its rate? With the congestion window cwnd — the amount of unacknowledged data allowed in the network at once. Data in flight = min(cwnd, rwnd).
  2. How does it detect congestion? From packet loss — a retransmission timeout, or 3 duplicate ACKs — and from rising delay (longer RTTs).
  3. What algorithm changes the rate? Slow start → congestion avoidance → fast retransmit → fast recovery.

Why it is called AIMD (write this if the question says "justify")

1. Additive increase. In congestion avoidance cwnd rises by 1 MSS per RTT — linear growth (slide: 8 → 9 → 10). TCP keeps probing upward until a loss shows the network is full.

2. Multiplicative decrease. On 3 duplicate ACKs the window is halved: ssthresh = cwnd/2, cwnd = ssthresh + 3 MSS (Reno). On a timeout: ssthresh = cwnd/2 and cwnd falls to 1 MSS. The decrease is a multiple (×½) of the current window, not a fixed amount.

3. Result — the sawtooth. cwnd climbs linearly, drops by half at each loss, climbs again.

4. Why it works. The gentle increase avoids causing congestion; the sharp decrease relieves it quickly; and competing connections using AIMD converge to a fair share of the link.

HookS-A-R-R = "Start slow, Avoid trouble, Resend fast, Recover." And remember: slow start is exponential — it is "slow" only in where it starts, not in how it grows.

Reading the graph out loud (examiners love this): initial ssthresh = 8. Slow start 1 → 2 → 4 → 8. At cwnd = 8 = ssthresh, congestion avoidance adds 1 per round up to 12. At round 8 a triple duplicate ACK signals loss → new ssthresh = 12/2 = 6. Tahoe drops to cwnd = 1 and slow-starts again; Reno goes to ssthresh + 3 = 9 and continues linearly.

If asked: "approaches to congestion control"

1. End-to-end. The network layer gives no explicit support. End systems infer congestion from packet loss (timeout or duplicate ACKs) and rising delay. This is classic TCP — cwnd + the four algorithms.

2. Network-assisted. Routers give explicit feedback. Example ECN: the congested router sets two ECN bits in the IP Type-of-Service field; the receiver echoes it using the ECE flag in the TCP ACK; the sender reduces its rate. Congestion is signalled without dropping packets.

One-line comparison: end-to-end must wait for a loss or delay to react; network-assisted warns earlier.

If asked: "fairness in TCP"

Fairness: if K TCP connections share a bottleneck of rate R, each should get R/K. For two connections with throughputs x and y: the equal-share line is x = y; full utilisation is x + y = R. Both additively increase (moving up at 45°); when x + y exceeds R the router drops packets and both halve, which halves the difference between them. Repeating, they converge to R/2 each whatever the starting point. AIMD is what produces fairness.

Problems in sharing: (1) UDP is not fair — multimedia apps don't back off and push TCP out; (2) parallel connections — a browser opening 9 connections against 1 gets ~9/10 of R; (3) the model assumes equal RTTs — shorter-RTT connections grow faster and take more bandwidth.

Go-Back-N with a lost frame, and the Selective Repeat window proof
asked 4× · came in CIE-1 Apr 2025 AND May 20245–8 marksCO2draw it
"Apply the concept of Go-Back-N to a scenario where a data frame is lost during transmission. Use a sequence diagram to show how the protocol handles it." CIE-1 Apr 2025 Q1b · CIE-1 May 2024 Q1c · SEE Feb 2024 Q3a · CIE-1 Jun 2021 Q2a (SR)

1. The idea

GBN is a reliable-data-transfer (ARQ) protocol. The sender may send up to N packets without waiting for ACKs. If a packet is lost, the sender goes back and retransmits that packet and every packet after it.

2. Sender

Keeps a window of size N with base (oldest unACKed packet) and nextseqnum (next to send). One timer runs, for the oldest unACKed packet. Uses cumulative ACKs: "ACK n" means all packets up to n arrived. On timeout it resends base … nextseqnum−1.

3 events (extended FSM): rdt_send(data) → if nextseqnum < base + N, make_pkt & send, start timer if base == nextseqnum, nextseqnum++; else refuse (window full). ACK received (uncorrupted) → base = acknum + 1; if base == nextseqnum stop the timer else restart it; a corrupt ACK is ignored. Timeout → restart timer and resend all unACKed packets.

3. Receiver

Accepts only the expected in-order packet (delivers it and ACKs it, expectedseqnum++). Any out-of-order or corrupted packet is discarded and the ACK of the last in-order packet is re-sent. The receiver has no buffer — that is the whole difference from Selective Repeat.

4. Sequence diagram — window N = 4, packet 2 lost

5. Drawbacks (needed for 8 marks)

  • Correctly received packets after the loss are thrown away and sent again → wasted bandwidth.
  • Poor performance on noisy networks, where losses are frequent — a single loss costs a whole window.

GBN numericals from the slides

Method: number every transmission including retransmissions, mark each 5th/6th as lost, and after a loss resend from the lost packet through the last one sent.

Selective Repeat — justify window ≤ 2m−1

With m-bit sequence numbers there are 2m distinct numbers (0 … 2m−1). In SR the receiver buffers out-of-order packets inside its window, so the sender window and receiver window must never overlap in sequence-number space: Wsender + Wreceiver ≤ 2m. With equal windows, W ≤ 2m−1.

Example, m = 2 (numbers 0, 1, 2, 3):

  • W = 3 (too big): sender sends 0, 1, 2. Receiver gets all three and slides its window to expect 3, 0, 1. All ACKs are lost. Sender times out and resends 0. The receiver is now expecting 0 as a new packet, so it accepts a duplicate as new data — an error.
  • W = 2 = 22−1: after receiving 0, 1 the receiver's window is 2, 3. The resent 0 is outside its window, so it is recognised as a duplicate and simply re-ACKed. Correct.

Conclusion: a window larger than 2m−1 lets the receiver confuse an old retransmission with a new packet. (In GBN the limit is 2m − 1 because the receiver window is only 1.)

TCP connection management — 3-way handshake, closing, and the client states
asked 3× incl. CIE-1 Apr 20255–6 marksCO2draw it

A. Connection establishment — 3-way handshake

  1. SYN. The client sends a segment with SYN = 1 and a randomly chosen initial sequence number client_isn. No data.
    Significance: asks to open the connection and tells the server where the client's byte numbering starts.
  2. SYN + ACK. The server replies with SYN = 1, its own server_isn, and ack = client_isn + 1; it allocates buffers and variables.
    Significance: agrees to connect, confirms the client's number and announces its own.
  3. ACK. The client sends SYN = 0, seq = client_isn + 1, ack = server_isn + 1, and allocates its buffers. This segment may already carry data.
    Significance: confirms the server's number — the connection is now ESTABLISHED.

Why three steps: each side must announce its own initial sequence number and have it acknowledged by the other. Two steps cannot do both.

B. Connection termination — 4 segments

  1. FIN from the client (no more data to send).
  2. ACK from the server — the client→server direction is now closed.
  3. FIN from the server (it has finished too).
  4. ACK from the client. All resources in both hosts are deallocated; the client first waits in TIME_WAIT (~30 s).

Why four: TCP is full-duplex, so each direction must be shut down separately.

Hook"SYN · SYN-ACK · ACK" to open, "FIN · ACK · FIN · ACK" to close. 3 to open, 4 to close — because closing is one-direction-at-a-time. TIME_WAIT exists so a lost final ACK can be re-sent and so old duplicate segments die out before the port is reused.

Flow control and the receive window (rwnd)
asked 4×5–6 marksCO2formula
"With suitable formulas, explain what happens if the network layer delivers data faster than the application layer removes it from the socket buffers." / "Explain the flow control mechanism in TCP along with the receiver window calculations." CIE-1 Jun 2023 Q3a · CIE-1 May 2024 Q3b · SEE Jan 2020 Q3b, Q3c

The problem: if data arrives faster than the application reads it, the receive buffer fills up and overflows — data is lost.

The solution: TCP flow control — a speed-matching service that matches the sender's rate to the receiving application's reading rate. (Do not confuse with congestion control, which protects the network; flow control protects the receiver.)

The receiver keeps RcvBuffer and two variables: LastByteRead (last byte the application read) and LastByteRcvd (last byte placed in the buffer). To avoid overflow:

LastByteRcvd − LastByteRead ≤ RcvBuffer

The free space is the receive window:

rwnd = RcvBuffer − [ LastByteRcvd − LastByteRead ]

The receiver puts rwnd in the receive-window field of every segment/ACK it sends. Initially rwnd = RcvBuffer. The sender then limits its unacknowledged data:

LastByteSent − LastByteAcked ≤ rwnd

When rwnd = 0 the sender stops — but keeps sending small probe segments so it learns when space frees up. When the application reads data, a larger rwnd is advertised and sending resumes.

Worked exampleRcvBuffer = 4096 B, LastByteRcvd = 3000, LastByteRead = 1000.
rwnd = 4096 − (3000 − 1000) = 2096 B. The sender may have at most 2096 bytes unACKed.
If the application then reads up to byte 3000, rwnd rises back to 4096 B.
The 100 Mbps questionA and B joined by a 100 Mbps link; A's app writes at 120 Mbps; B's app reads at only 50 Mbps.
Data can arrive at B at up to 100 Mbps (A's TCP cannot exceed the link) while B drains at 50. So B's buffer fills, its ACKs advertise a shrinking rwnd, and eventually rwnd = 0 → A stops (probing). Long-run: A's average sending rate settles at ≈ 50 Mbps, the link is only ~50 % utilised, and A's own send buffer fills so its application is throttled from 120 down to ≈ 50 Mbps too.

Buffering (if asked separately): the sending process writes to its socket; TCP places the data in the send buffer, cuts it into segments (data ≤ MSS) and sends them. The receiving TCP places arriving data in the receive buffer and the application reads from it at its own pace. Buffers exist because the application and the network run at different speeds.

Hook"rwnd protects the receiver, cwnd protects the network." Data actually in flight = min(cwnd, rwnd). And rwnd = bucket size − water in it.

Multiplexing and demultiplexing — connectionless and connection-oriented
asked 4×5–7 marksCO2draw it

  • Multiplexing (sender): the transport layer gathers data from several application processes (through their sockets), adds a header with the source and destination port numbers to each chunk to form a segment, and passes the segments down to the network layer.
  • Demultiplexing (receiver): the transport layer examines the port-number fields of each incoming segment, finds the correct socket and delivers the data to that process.
  • Why needed: many applications (browser, chat, email, FTP) share one host and one network connection.

Connectionless demultiplexing — UDP

A UDP socket is identified by a 2-tuple: (destination IP, destination port). No handshake; every datagram is independent. The receiving host picks the socket using the destination port alone.

Example (Fig. 3.4): Host A's client process has socket port 19157 and sends a datagram to Server B's port 46428. The segment carries source 19157, destination 46428. At B, UDP reads destination port 46428 and delivers to the process bound to it. B's reply swaps the ports — source 46428, destination 19157 — so A's UDP delivers it to the client process. If another host C also sends to port 46428, its datagram goes to the same socket; only the source IP/port differ, and they are used for the reply.

Connection-oriented demultiplexing — TCP

A TCP socket is identified by a 4-tuple: (source IP, source port, destination IP, destination port). A connection is set up by a handshake first. When a segment arrives the host checks all four values and delivers it to the matching connection socket — so two segments with the same destination port can still go to different sockets.

Example (Fig. 3.5): web clients A and C connect to Web Server B on port 80.

A → B : (A, 26145, B, 80) C → B : (C, 26145, B, 80) same ports, different source IP C → B : (C, 7532, B, 80) different source port

The server therefore has three different sockets, each served by its own HTTP process, even though all three use destination port 80.

UDP — why applications choose it, segment structure and checksum
asked 3× incl. CIE-1 May 20245–7 marksCO2

4 reasons to choose UDP

  1. Finer application-level control. As soon as the application passes data, UDP wraps it in a segment and sends it. TCP may delay data (connection setup, congestion control, retransmission) — real-time apps cannot afford that.
  2. No connection establishment. No three-way handshake, so no setup delay — this is exactly why DNS uses UDP.
  3. No connection state. UDP keeps no buffers, no sequence/ack numbers, no congestion parameters, so a server can support many more active clients.
  4. Small header — 8 bytes vs TCP's 20 bytes. Less overhead per packet.

Examples: internet telephony and video calls (delay-sensitive, tolerate a little loss), DNS, SNMP, NFS. Reliability can still be built into the application if needed.

The 4 header fields

  • Source / destination port (16 bits each) — identify the sending and receiving processes (multiplexing/demultiplexing).
  • Length (16 bits) — total length of the UDP segment (header + data) in bytes.
  • Checksum (16 bits) — error detection over the segment. Optional in IPv4, mandatory in IPv6.

UDP checksum — the standard example

Sender: 1's complement of the sum of all the 16-bit words, wrapping any carry back in.

0110011001100000 + 0101010101010101 ---------------- 1011101110110101 + 1000111100001100 ---------------- 0100101011000010 (carry wrapped) 1's complement → checksum = 1011010100111101

Receiver: adds all four 16-bit words including the checksum:

0100101011000010 + 1011010100111101 ---------------- 1111111111111111 → all 1s, NO ERROR

A 0 anywhere in the result means the segment was corrupted.

The TCP sender has exactly 3 events. Variables: NextSeqNum (sequence number of the next byte to send) and SendBase (sequence number of the oldest unacknowledged byte).

NextSeqNum = InitialSeqNumber SendBase = InitialSeqNumber loop (forever) { switch (event) event: data received from application above create TCP segment with sequence number NextSeqNum if (timer not running) start timer pass segment to IP NextSeqNum = NextSeqNum + length(data) event: timer timeout retransmit the not-yet-ACKed segment with the smallest sequence number start timer event: ACK received, with ACK field value y if (y > SendBase) { SendBase = y if (any not-yet-ACKed segments) start timer } }

Explanation of the 3 events:

  1. Data from the application — TCP makes a segment whose sequence number is the byte-stream number of its first byte, starts the timer (the timer always runs for the oldest unACKed segment, with interval TimeoutInterval), sends it to IP and advances NextSeqNum by the data length.
  2. Timeout — the ACK did not arrive in time, so TCP assumes loss. It retransmits the unACKed segment with the smallest sequence number and restarts the timer (most implementations also double the interval).
  3. ACK received — ACKs are cumulative. If y > SendBase then everything before y is acknowledged, so SendBase = y; if segments are still unACKed the timer is restarted.
The classic sumB has received all bytes through 126. A sends two segments back-to-back: 80 bytes with Seq = 127 (source port 302, dest 80) and 40 bytes with Seq = 207.
(i) First arrives first → B has bytes through 206, so ACK = 207, source port 80, destination port 302 (ports swap in the reply).
(ii) Second arrives first → B still hasn't got byte 127, so ACK = 127.
(iii) If the first ACK is lost and the second arrives after A's timeout: A retransmits Seq = 127; B discards the duplicate and sends ACK = 247. Because ACKs are cumulative, ACK = 247 tells A all bytes up to 246 arrived, so only segment 1 was retransmitted.

Always write: ACK number = next expected byte = last byte received + 1.

3. The need for CIDR (classless addressing)

Why classless is more efficient (the marks sentence)

The block matches the requirement. A company needing 50 addresses receives a /26 (64 addresses, 62 usable) instead of a whole class C (256, wasting 204). Because every allocation is sized to need:

IPv4 datagram format

Datagram = header (20–60 bytes) + payload, total 20–65,535 bytes. IPv4 is connectionless with no delivery guarantee.

  • VER (4) = 4 · HLEN (4) = header length in 4-byte words, 5–15 → 20–60 bytes.
  • Service type (8) — QoS: precedence, delay, throughput, reliability.
  • Total length (16) — header + data in bytes; data = total length − HLEN × 4.
  • Identification (16) — packet ID, same for all fragments of a datagram.
  • Flags (3) — unused, DF (don't fragment), MF (more fragments).
  • Fragmentation offset (13) — position of the fragment's data, in 8-byte units.
  • TTL (8) — hop limit, stops datagrams looping.
  • Protocol (8) — ICMP 1, TCP 6, UDP 17.
  • Header checksum (16) — checks the header only; a bad header is discarded.
  • Source / destination address (32 each) · Options (0–40 bytes).

Fragmentation

Definition: dividing an IP datagram into smaller datagrams (fragments) so each fits in the frame of the next network.

Need: a datagram passes through different physical networks, each with its own MTU (maximum transfer unit — the largest frame payload it can carry): Ethernet 1500, FDDI 4352, PPP 512. When the datagram is bigger than the next network's MTU it cannot be sent as it is, so the router (or source host) splits it.

Rules: the fragmenting device changes flags, fragmentation offset and total length (other fields are copied, the checksum is recalculated). All fragments carry the same identification; offset is in 8-byte units; MF = 1 on all but the last. Only the final destination reassembles.

The five most common mark-losers
  1. Using the old EstimatedRTT inside DevRTT. Compute EstimatedRTT first, always.
  2. Writing only "64 addresses" when the question says valid — write 64 in the block, 62 usable.
  3. Allocating the smallest subnet first, so later blocks don't start on a multiple of their size.
  4. Describing GBN but drawing no discard + re-ACK arrows — that is where the marks are.
  5. Writing prose with no diagram for an "Illustrate/Draw/Show" verb. Those verbs are worth 2 marks of picture.

Final 60 seconds — the three sentences to carry in

Unit 1. Every application-layer answer is client + server + protocol + port + a numbered message exchange. If you can name the two endpoints, the port and the order of messages, you have the marks.

Unit 2. Everything is one of two windows. rwnd = what the receiver can take. cwnd = what the network can take. Loss is detected by timeout or 3 duplicate ACKs, and those two events have different recoveries.

Unit 3. Four lines solve everything: N = 232−n, mask = n ones, first = AND, last = OR NOT. Round up to a power of two, allocate largest first, and always state the leftover.
